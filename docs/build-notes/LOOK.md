## The idea (what the user asked for)
Once you generate an image or animation in a post, later ones should carry the same look and feel (not the same content). A post has one **look**; it is set automatically from the first image/animation, or by "Use as the look" on any block, or by describing/picking one; it is passed into every later generation; blocks made before the look existed (or before it changed) are tagged "off-look" and can be restyled one at a time or all together — never automatically. Looks can be saved and reused, and one can be the site default. Each generation can opt out ("Use post look" switch).

Rules:
- Effective look = `post.look ?? settings.defaultLook` (`effectiveLook`).
- **Code snippets** follow the look only through `look.codeTheme`, applied at render time (site and editor). They are never off-look and never restyled.
- **Images**: the look's text goes into the prompt and `look.referenceUrl` (if any) is sent as a style reference. Stamp `data.look = stampOf(look)` when generated with the look, `null` when the switch was off.
- **Animations** read colours and fonts from a `theme` prop (`MotionTheme`) instead of hard-coding them, so restyling is a re-render with a new theme and no AI call. `data.look` stamps the rendered asset. Old compositions that hard-code colours (`!usesTheme(code)`) need one AI conversion first.
- **Video clips**: look text goes into the prompt. Restyle = regenerate, per block only (not part of "Restyle all").

## Motion code contract v2 (replaces PHASE2.md's)
```tsx
import { AbsoluteFill, interpolate, spring, useCurrentFrame, useVideoConfig } from "remotion";
export const config = { durationInFrames: 150, fps: 30, width: 1280, height: 720 };
export default function Motion({ theme }: { theme: Theme }) { /* … */ }
type Theme = { bg: string; ink: string; accent: string; muted: string; extra: string[]; titleFont: string; bodyFont: string; monoFont: string };
```
Every colour and font-family comes from `theme` (tints via opacity or `interpolateColors` between theme colours). No hex literals. Compositions written before v2 ignore the prop and keep working.

## Stream L1 — backend
Files: `lib/store/file.ts`, `lib/store/postgres.ts`, `app/api/posts/**`, `app/api/settings/route.ts`, `lib/prompts.ts`, `lib/openrouter.ts`, `app/api/ai/studio/route.ts`, `app/api/ai/image/route.ts`, `app/api/ai/video/route.ts`, new `app/api/ai/look/route.ts`, new `app/api/ai/restyle/route.ts`.
- Stores: persist `Post.look` (Postgres: `alter table posts add column if not exists look jsonb` in the lazy init; existing rows read as null) and the two new settings. `createPost()` → `look: null`. Summaries include `look`.
- `PATCH /api/posts/[id]` accepts `look` (`null` clears; otherwise `validateLook` → 400 if invalid). `PATCH /api/settings` accepts `defaultLook` (same rule) and `savedLooks` (array, each validated, invalid ones dropped, max 20). Changing a post's look or the default look revalidates public paths (code theme changes how posts render).
- `POST /api/ai/look` body `{ source: {kind:"image"; url: string; prompt?: string} | {kind:"motion"; code: string} | {kind:"text"; description: string}, post?: {title: string; text: string} }` → `{ look: Look }`. Job `look`. Image: send the picture to the model as an image content part (resolve stored media with the existing `referenceUrl`/media helpers so local `/media/...` files work — data URL; verify the multimodal message format in OpenRouter's docs via WebFetch of https://openrouter.ai/docs/llms.txt) plus the prompt that made it; ask for the STYLE only — palette actually present in the image, medium/line/texture/lighting in one or two sentences, mood words, a fitting code theme from `CODE_THEMES` (dark page-like looks → a dark theme etc.), a short name. The result's `referenceUrl` is the image URL. Motion: read the code — colours used, fonts, pacing. Text: invent a coherent look from the description. Always JSON out → `validateLook(parsed, { id: crypto.randomUUID(), version: 1 })`; 502 with a readable error if it doesn't validate. Mock (`AI_MOCK=1`): deterministic look named "Mock look" with palette bg #10141c, ink #e8edf5, accent #4cc9f0, muted #2a3342, sans titles, codeTheme "night-owl", and `referenceUrl` for image sources.
- `POST /api/ai/restyle` body `{ code: string }` → `{ code: string }`: job `motion`; rewrite a composition to contract v2 — replace every hard-coded colour/font with the nearest `theme` token, change nothing else (layout, timing, text). Validate the reply still parses with `extractArtifact` and satisfies `usesTheme`; else 502. Mock: return a small v2 composition.
- `motionSystem()` → contract v2 (theme prop mandatory, no hex literals; the prompt no longer lists the blog palette — it says the theme carries the colours). `MOCK_MOTION` → v2 (uses `theme.bg`, `theme.ink`, `theme.accent`, `theme.muted`, `theme.titleFont`).
- `look?: Look | null` added to the bodies of `/api/ai/studio` (kind "motion": pass pace/mood/illustration feel as guidance — colours come from the theme prop; kind "code": ignored), `/api/ai/image` (fold `lookToPrompt(look)` into the prompt-writing step so the final image prompt carries the style; send `look.referenceUrl` as an extra input reference with an instruction to match its style, not its content; return `image.look = stampOf(look)` — `null` when no look was sent) and `/api/ai/video` (append the look description to the prompt). Validate with `validateLook`; ignore if invalid.

  - "Clear look" (→ `onChange(null)`, behind a confirm).
- Settings page: a "Default look" row showing the default look's name + swatches, with "Remove" — editing happens in the post's Look sheet.
